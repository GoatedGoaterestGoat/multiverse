# Codex

`settings.inbox_bridge` defaults to auto when absent: each spawn/resume tries the bridge, then launches plain with a recorded reason if preparation is unavailable. Set `true` to require the bridge and fail on errors, or `false` to always launch plain. Base, development and testing templates all use auto. Claude and Pi retain their opt-in behavior. Existing explicit settings are preserved.

Auto reuses daemon startup/socket checks and checks CLI `--help` for `--remote`; it does not start another service or speculative conversation. Missing daemon support, startup/config RPC failure or unavailable local relay preparation can select plain before the child starts. Bridge-incompatible launch preferences also produce a recorded plain fallback; invalid settings remain errors. After a native child starts, identity or permission failures never trigger a plain restart. Inspect `runtime.json.native_mode` for `policy`, `mode` and `fallback_reason`; `mv2 capabilities --agent AGENT` reports that selection in its spawn/resume reasons, and the dashboard inspector displays it. Resume reevaluates availability and keeps the saved UUID, workspace and native storage.

This JSON configuration references the source-owned Codex adapter package. CLI flags were checked against Codex 0.163.0 and the [official reference](https://developers.openai.com/codex/cli/reference/). It uses the installed CLI, account, model defaults, permissions and project context. No hooks or MCP server are installed. Plain mode passes the universe bootstrap through `developer_instructions`. Bridge mode adds it to the native thread request through a launch-local relay, preserving any instructions already in that request. No native configuration files are rewritten.

Managed Codex terminals suppress startup update dialogs and banners with `-c check_for_update_on_startup=false` on spawn and resume, including wake prompts, in plain and bridge modes. An explicit value for this key in the applicable `args`, `spawn_args` or `resume_args` takes precedence; mv2 does not add a second value. Set it to `true` there to restore native update prompts. The override stays before `--` and is honored by the remote TUI. Native configuration files and the daemon's separate automatic-update policy are unchanged.

Shared daemon startup runs from the user's home directory; agent terminals and threads still use their saved workspace. This prevents a deleted worktree or temporary universe from breaking the daemon. If an older daemon reports `failed to resolve feature override precedence: No such file or directory`, use the explicit restart command in the launch diagnostic, with the same `CODEX_HOME`, only when other Codex work is idle. Then retry resume. mv2 never restarts the shared daemon automatically.

On spawn and resume, bridge mode names the native thread after the mv2 agent with `thread/name/set`, after validating and binding its exact ID/workspace. This includes an empty new thread and reapplies the mv2 name on resume. The control request has a three-second bound; a failure is recorded in `runtime.json` while the terminal stays usable. The `session_name` capability reports this support. Plain Codex has no CLI name flag and reports naming unavailable. Naming was exercised with Codex 0.163.0.

Codex chooses its session UUID. In bridge mode, core records the exact thread ID and workspace from the native launch reply automatically, as soon as the TUI creates or resumes its thread. In plain mode, the startup instruction asks the model to run `"$MV2_CLI" session-bind --session-id "$CODEX_THREAD_ID"` from its shell tool before working. This records `native_session_id` in the agent's properties. An inherited parent thread ID is removed before launching. Resume uses only that recorded UUID, never `--last` or a name search. If startup was interrupted before registration, bind the exact UUID shown by Codex's `/status` or exit message with `mv2 session-bind --agent AGENT --session-id UUID`. Plain-mode registration is prompt-driven, not a guaranteed lifecycle callback.

Messages remain in the core inbox with delivery tracking. `mv2 inbox` shows unread inbox-only messages and marks them read automatically; `mv2 inbox --all` browses the full raw history. Native messages contain the sender line and message text. Use `mv2 deliver AGENT --check` to reconcile uncertain delivery and `--retry` to retry definite failures. A live plain session cannot receive native delivery. In auto or required bridge mode, spawn/resume asks `codex app-server daemon start` to start or reuse the shared daemon for your OS user and `CODEX_HOME`, then connects the native TUI through a private relay in the launch runner. The relay adds bootstrap instructions and writable roots to the native thread request because Codex 0.163.0 drops the former and rejects `--add-dir` in remote TUI mode. Multiple agents/projects/monitors share that daemon. Closing Multiverse does not stop it. CLI and daemon versions may differ: actual protocol checks decide bridge availability. `runtime.json.native_versions` records both at launch; capabilities and the inspector show them, highlighting a difference without blocking spawn/resume. Codex manages its daemon package during native startup; Homebrew Codex 0.163.0 is supported. Multiverse never invokes daemon installation, update, restart or stop commands. `mv2 send AGENT --text TEXT --delivery steer|follow-up` supports native safe-boundary steering and after-turn follow-up, including idle wake. Acceptance does not confirm that the agent has read or answered a message. After an interrupt, Codex can accept a message while automatic queue draining remains paused. For idle delivery, mv2 explicitly starts the exact newly accepted entry only when it is alone in the queue. It never resends the text or skips older queued work; start failures preserve acceptance with a diagnostic. Use `deliver AGENT --check` to inspect evidence rather than resending. Use `mv2 capabilities --agent AGENT --probe` to check the current exact session. Put sandbox/approval flags needed on both spawn and resume in `args`; `resume_args` applies them only on resume. The relay translates explicit `--dangerously-bypass-approvals-and-sandbox`, `--sandbox` / `-s` and `--ask-for-approval` / `-a` into the exact `thread/resume` request and checks the effective native reply. Without those flags it preserves native TUI request behavior; a prior full-access launch is not guaranteed to remain full-access. Required bridge mode rejects unsupported `--profile`, `--add-dir` and `--approve-for-me` resume flags; auto selects plain for those flags with a reason. Writable-root config overrides on resume remain errors. Put initial-only settings in `spawn_args`. Invalid permission values remain errors. Initial writable-directory flags are translated to equivalent native thread settings; native configuration files are unchanged. Terminal liveness is observed. In bridge mode, after the exact session ID is bound, the launch runner watches app-server status: active work is `working`, approval or user-input waits are `waiting`, and idle is `idle`. Other native states, a missing binding, or a disconnected status watcher give `unknown`; plain mode stays `unknown`. Loss of the primary terminal relay shows `disconnected` while the process remains alive. The inspector and list output show recovery guidance, and `runtime.json.native_relay` records the failure. New sends are refused and stay saved for explicit retry; exact-thread receipts and cancellation remain available if the daemon is reachable. Kill then resume the launch (or spawn again if it never bound a native session). Qualified idle terminals can restart automatically as described below; all other relay losses require manual recovery. No daemon restart or message replay is attempted. Status is detected automatically, never set by agents. The relay and watcher close with the launch. The watcher filters events by the bound thread ID; it never resumes a thread or answers a prompt. Native `/multiverse` slash commands are not registered: send `Please run /multiverse list` as ordinary text, or use `mv2 catalog` from a shell.

One Codex conversation is one mv2 agent, whether driven from mv2's terminal or the user's own Codex client on the same server. Bridge shell `report`, `inbox` and message sender identity are agent-scoped and keep working across terminal launches. The tool environment uses explicit `codex-agent-v1` mode and stable agent/native proof; it contains no `MV2_LAUNCH_ID` or launch-private socket paths. Missing proof is an error. The frontend relay, runner binding/runtime writes, and target pane/process control remain generation-strict. In stable agent mode, `session-bind` may only verify the identical already-bound UUID without writes; new bridge bootstrap relies on the relay. Plain binding is unchanged. Restart running Codex bridge agents once after updating: `mv2 kill NAME`, then `mv2 resume NAME`, with no other client attached so Codex releases and reloads the conversation. Old per-launch conversation values receive explicit restart guidance, not a legacy-authority bypass.

A separate native writer can cause Codex to say `This conversation is open in another app` / `already has an active writer`. mv2 keeps that native refusal as this launch's error, even if R later succeeds in Codex. Use `mv2 kill NAME --attachment-only` to close only mv2's refused frontend and await its cleanup, then run a new `mv2 resume`; do not cancel the conversation's work merely to close our terminal. Same-server sharing that Codex accepts is not a refusal. Uncertain native or plain wake prompts are never automatically replayed.

For startup problems, use `mv2 inspect AGENT`, inspect `runtime.json`, and check `codex --help`. Authentication, workspace trust and permission prompts remain native and may require attaching. Launch/resume identity, busy timing and idle wake are tested with an installed native TUI and local scripted provider. Authenticated model turns are not part of the offline suite. Native service failures are logged in the launch directory.

Explicit `mv2 kill AGENT` (`stop` is an alias) cancels that exact native thread's queued work, active turn and background terminals before terminating its native process and removing its tmux wrapper. Live progresses through ending, stopped and dormant; a running native session exit detaches clients viewing its pane and removes its wrapper automatically; startup failures retain a stopped wrapper and diagnostic. Resume accepts stopped and dormant agents. It also works after the pane is gone and reports cancelled queue entries, turn interrupts and background-terminal cleanup. Native cancellation requires a bound native ID and a reachable server. If cancellation fails after the process has exited, kill still removes its stopped wrapper and reports cancellation as unconfirmed; retry stop when the daemon is reachable. The shared daemon and sibling threads remain running. Confirmed cancelled messages stay in the inbox history and are not automatically retried. Merely disconnecting a native terminal can leave work running.

Plain launches pass the bootstrap with `-c developer_instructions=...`. Codex may warn that command-line configuration overrides require embedded mode rather than its default shared background server. Selected bridge mode connects with `--remote unix://...`. Existing running terminals keep their mode; an unset profile uses auto at its next spawn/resume.

Bridge mode also reports measured context usage from native token notifications. The dashboard shows the latest request's tokens and the model context window; cached tokens are already included. Its percentage matches Codex's native 12,000-token baseline adjustment, so it can differ from the raw tokens/window ratio. The relay accepts observations only for its validated thread and core stores them in the current launch's runtime. Resume can replay the native reading without a model call. Until a reading arrives, usage is N/A; after disconnecting, the last reading keeps its timestamp. Plain mode, cumulative token totals, cost and rate limits remain unavailable. Existing terminals need a relaunch to load a newly installed relay implementation.

Bridge launches remain `starting` until their native reply validates and binds. New launches save incoming messages until binding and permission validation finish; older runners retain their binding-time refusal until relaunched. If an already-loaded thread ignores a requested grant, the relay records the mismatch in `runtime.json` and refuses new input for that launch. A shared Codex conversation keeps its current grants. Use those grants or deliberately change them through Codex before a new mv2 resume. Shared clients are normal; manual attachment does not require them to detach or the conversation to become idle. Multiverse never forces an unload or restarts the shared daemon. A local scripted-provider test verifies exact plain-to-bridge and repeated bridge resumes with bypass in `args`, including Unix socket creation and `.git` writes.

Use `spawn --wait` or `resume AGENT --wait` to wait for the exact bridge binding and validated permissions before sending. `--wait-timeout SECONDS` defaults to 60. A timeout returns the latest state with `ready: false` and `timed_out: true`, exits nonzero, and leaves the launch running. Plain launches wait for native child startup and surface a recognized native ownership refusal; a live process cannot clear that refusal.

Steer/follow-up to a stopped or dormant agent resumes the saved UUID with the framed sender and text as the positional prompt in `codex resume`, including plain mode. The terminal stays interactive; no app-server message delivery is used for this first prompt. The `wake` capability reports support. Process startup is recorded as accepted with consumption unconfirmed. Subsequent messages to a starting bridge stay pending until validated binding and acceptance of the TUI starting turn, then drain in order. Startup failures remain saved for explicit retry; accepted or uncertain prompts are never replayed. Inbox-only never wakes. Dashboard `m` uses the same path.

On spawn and resume, core enables tmux mouse handling only for this Codex adapter wrapper's session, including plain and bridge modes. The wheel scrolls Codex's transcript. Global tmux options, key bindings, alternate-screen behavior and other sessions stay unchanged. Existing terminals need a resume to pick up this launch setting; legacy schema-1 profiles keep their existing behavior.

Disconnected bridge sessions can recover automatically when the runner has a recent exact-thread idle proof and fresh checks confirm no active turn, approval/input wait, queued or uncertain messages, startup delivery, background terminals or local terminal children. The worker checks the existing endpoint at most five times with backoff; it never starts or restarts a daemon or replays input. It resumes the same saved thread with normal workspace and effective-permission validation, refreshes the wrapper status bar, and retains last-known context with its original timestamp. The same pane and attached viewers remain; the conversation redraws, but unsent drafts cannot be preserved. Unsafe or uncertain sessions stay disconnected with a reason. At most two automatic restarts occur in five minutes. `runtime.json.auto_recovery` and bounded `automatic_restarts` record the outcome; `list`, `inspect` and `doctor` show a successful reconnect as a note. Existing launches without `attachment` and `native_service` runtime records need an explicit resume to enable recovery.

The adapter declares an externally owned native service, its exact conversation and a separate terminal attachment. Core records the provider and canonical storage scope (`CODEX_HOME`, plus `CODEX_SQLITE_HOME` when selected), preserving them across resume; a changed scope is refused. The service may restart at the same endpoint without changing identity. Recovery is explicitly enabled for this bridge, uses only that saved endpoint and requires a validated native binding; an RPC relay alone does not enable it. Plain mode has no recovery monitor. Provider protocol and safety interpretation stay in the Codex adapter; core owns transports, locks, retry bounds and pane replacement.

Compatibility was rechecked with Codex 0.163.0 using isolated native homes and a local scripted provider, without model calls. The plugin config and MCP minimum support versions remain 0.159.3 and 0.162.1 respectively. Native `/new` and `/clear` request a new conversation, and in-TUI `/resume` can request another one; the bridge rejects these identity changes once bound. Start a separate mv2 agent or resume the intended agent through mv2. The 0.163.0 cold-resume permission fixes do not remove the bridge permission translation: remote TUI resume requests still omit explicit sandbox and approval overrides.
